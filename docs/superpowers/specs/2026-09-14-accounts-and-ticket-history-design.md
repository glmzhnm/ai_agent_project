# Аккаунты и история тикетов в PostgreSQL

Дата: 2026-09-14
Статус: одобрено, готово к написанию плана реализации

## Контекст

Сейчас у ассистента дежурной смены нет ни авторизации, ни постоянного
хранилища истории: последние 5 вопросов/ответов лежат в `localStorage`
браузера (`frontend/src/hooks/useHistory.js`) и видны только тому, кто их
задал, в этом же браузере. Задача — перенести историю («тикеты») в
PostgreSQL и закрыть сайт логином, сохранив общий, командный характер
истории.

Это первый из двух подпроектов. Второй — общий редизайн UI/UX
(официальнее, понятнее, легче в использовании) — сознательно вынесен в
отдельный спек и делается после этого, чтобы не переписывать вёрстку
дважды.

## Требования

- Доступ к сайту закрыт логином/паролем — без входа приложение не открыть.
- История тикетов **общая на всю команду**: любой залогиненный видит все
  тикеты, а не только свои. Логин — это гейт доступа, не разграничение
  видимости данных.
- Тикеты, помеченные моделью как `escalate: true`, визуально выделяются
  красным в боковой панели.
- Аккаунты создаются только вручную, через CLI-скрипт на сервере —
  публичной регистрации нет.
- Хранить все тикеты бессрочно; в боковой панели — поиск по тексту вопроса
  и постраничная подгрузка (не всё сразу).
- PostgreSQL поднимается локально через Docker Compose.

## Архитектура

### Модель данных

```sql
users
  id            bigserial primary key
  login         text unique not null
  password_hash text not null
  created_at    timestamptz not null default now()

tickets
  id            bigserial primary key
  author_id     bigint not null references users(id)
  question      text not null
  mode          text not null                    -- engineer | client | escalation
  answer        jsonb not null                    -- весь объект Answer как есть
  meta          jsonb not null                    -- provider/model/latency/degraded
  escalate      boolean not null default false    -- денормализовано из answer.escalate
  created_at    timestamptz not null default now()

schema_migrations
  version       text primary key
  applied_at    timestamptz not null default now()

index tickets(created_at desc)
index tickets(escalate) where escalate = true
```

`answer` и `meta` хранятся целиком как `jsonb`: они уже валидируются
pydantic-схемами `Answer`/`Meta` до записи, дублировать их поля в
отдельные SQL-колонки незачем. `escalate` вынесен отдельной колонкой,
потому что по нему фильтруем и подсвечиваем в UI — доставать это из
глубины `jsonb` на каждый рендер накладно и неудобно для индекса.

### Работа с БД

Подход: **raw SQL + `asyncpg`**, без ORM. Обоснование: в проекте уже
принят принцип «минимум зависимостей, весь контроль на виду» — так,
`llm_client.py` сознательно обходится без SDK провайдеров ради контроля
через `httpx`. Для двух таблиц ORM (SQLAlchemy/SQLModel) + Alembic —
избыточный вес и лишний слой абстракции.

Миграции — пронумерованные файлы `backend/migrations/0001_init.sql`,
`0002_...` и т.д. Список применённых версий хранится в таблице
`schema_migrations`. При старте бэкенда (в `lifespan` FastAPI) ранер
проходит по файлам по порядку и применяет ещё не применённые; повторный
запуск — no-op. После миграций поднимается пул соединений `asyncpg` и
кладётся в `app.state`.

### Авторизация

- `POST /api/auth/login {login, password}` — сверяет пароль через
  `bcrypt`, при успехе выпускает JWT (`user_id`, `login`, `exp`) и кладёт
  его в `httpOnly`-cookie (`Secure`, `SameSite=Lax`).
- `POST /api/auth/logout` — стирает cookie.
- `GET /api/auth/me` — `{login}` при валидной cookie, иначе `401`.
- Остальные маршруты (`/api/ask`, `/api/tickets`) защищены FastAPI-
  зависимостью, проверяющей JWT из cookie; без валидного токена — `401`.
- Ошибка входа всегда общая — «Неверный логин или пароль» — без уточнения,
  что именно неверно (не даём угадывать существующие логины).
- Аккаунты создаются только через `python -m app.cli create-user --login
  ivan` — пароль вводится интерактивно через `getpass`, чтобы не оседал в
  истории шелла. Хешируется `bcrypt`, пишется в `users`. Понятная ошибка
  при попытке создать дубликат логина.

### API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/auth/login` | вход, ставит cookie |
| POST | `/api/auth/logout` | выход, стирает cookie |
| GET | `/api/auth/me` | проверка текущей сессии |
| POST | `/api/ask` | как сейчас, + требует авторизацию, + пишет тикет в БД после ответа модели, возвращает его вместе с `id` |
| GET | `/api/tickets` | `?limit=20&offset=0&q=текст` — список тикетов всей команды, сортировка по `created_at desc`, поиск подстрокой по `question` |

Пагинация — простая `limit/offset`. Курсорная пагинация была бы точнее
под нагрузкой, но для внутреннего инструмента команды из нескольких
человек это ненужное усложнение (YAGNI).

### Инфраструктура

- `docker-compose.yml` в корне проекта: сервис `db` (`postgres:16`) с
  volume для персистентности данных между перезапусками.
- `.env` / `.env.example`: добавляется `DATABASE_URL=postgresql://
  assistant:...@localhost:5432/assistant`.
- CORS: добавляется `allow_credentials=True` в `CORSMiddleware` — иначе
  браузер не приложит `httpOnly`-cookie к запросам с фронтенда (`:5173`)
  на бэкенд (`:8000`).

### Фронтенд

- Новый компонент `LoginForm`: поля логин/пароль, `POST /api/auth/login`.
- `App.jsx` при монтировании дёргает `GET /api/auth/me`:
  - `401` → рендерится только `LoginForm`, остальной интерфейс скрыт.
  - `200` → рендерится текущее приложение + кнопка «Выйти» в шапке рядом
    со `StatusBar`.
  - Если любой последующий запрос (`/api/ask`, `/api/tickets`) вернул
    `401` (сессия истекла) — сброс в состояние логина, а не показ как
    обычной ошибки сети.
- `useHistory.js` (localStorage) заменяется на `useTickets.js`: грузит
  `GET /api/tickets` при старте; после успешного `/api/ask` новый тикет
  добавляется в начало списка локально, без повторного похода на сервер.
- `HistoryList.jsx`: добавляется строка поиска (с дебаунсом, дёргает
  `?q=`) и кнопка «Показать ещё» (увеличивает `offset`). Кнопка «Очистить»
  убирается — это теперь общий журнал команды, а не личный кэш браузера,
  удалять его по кнопке некому.
- Тикет с `escalate: true` получает красную полосу/фон на основе уже
  существующих CSS-токенов `--danger` / `--danger-soft` (они уже есть в
  `styles.css`, ничего нового вводить не нужно).

## Обработка ошибок

- Неверный логин/пароль → общее сообщение, без уточнения деталей.
- Просроченный/невалидный JWT → `401` → фронт возвращает на экран логина.
- БД не поднялась при старте бэкенда → падаем сразу с понятным логом
  (аналогично нынешнему поведению при отсутствии ключа модели).
- БД недоступна при чтении тикетов → `ErrorBanner` с retry, как для
  прочих сетевых ошибок.
- БД недоступна при записи тикета после успешного ответа модели → ответ
  всё равно возвращается пользователю, ошибка записи только логируется на
  сервере. Ответ ассистента важнее факта его архивации.

## Тестирование

В проекте сейчас нет тестов вовсе — ни на бэкенде, ни на фронте. Так как
добавляется код с высокой ценой ошибки (пароли, токены, SQL), вводится
`pytest` + `pytest-asyncio` с покрытием:

- хеширование и проверка пароля;
- выпуск и проверка JWT, включая истёкший и подделанный токен;
- ранер миграций — применяет по порядку, повторный запуск — no-op;
- вставка/чтение/поиск тикетов в реальном тестовом Postgres (тот же
  `docker-compose`, отдельная тестовая БД).

Фронтенд-тесты не добавляются — их не было и до этой задачи, вводить
инфраструктуру тестирования UI ради одной фичи непропорционально задаче.

## Вне рамок этого спека

- Редизайн UI/UX — отдельный спек, делается после этой фичи.
- Разграничение видимости тикетов между пользователями (личная история,
  роли, права) — сознательно не делается: история общая на всю команду.
- Восстановление пароля, ротация JWT-секрета, множественные сессии на
  пользователя — не требуется для внутреннего инструмента с ручным
  созданием аккаунтов.
